# Decisions

Where the specification is silent, the code chooses the safer behaviour and records it here (CLAUDE.md, spec B4).
Each entry names the phase that made it. Security-, wire- or screen-changing questions go to `OPEN_QUESTIONS.md` first.

| ID | Phase | Decision | Why |
|---|---|---|---|
| D-001 | setup | The monorepo root is `Pehchaan/`. The finished frontend was **copied** into `apps/web`; the old `Pehchaan/frontend/` folder is a stale copy, excluded from git locally (`.git/info/exclude`), for the team to delete. | Decided by the team (2026-09-26). The build session was running inside `frontend/`, and Windows cannot move a folder a process is using. |
| D-002 | 1 | Type checking uses **TypeScript 7** (`tsc`, the native compiler) in every package. ESLint uses `typescript-eslint` 8 with **TypeScript 6.0** installed only at the repository root, as the parser's library. Lint rules are the non-type-aware recommended sets. | TypeScript 7 ships no JavaScript compiler API, and `typescript-eslint` supports TypeScript `<6.1`. pnpm's isolation gives each package its own `tsc`. |
| D-003 | 1 | Code targets **Node 22** APIs, Docker images use `node:22-bookworm-slim`, and `engines` is `>=22`. The build machine runs Node 24 LTS, which is compatible. | Spec section 3 and 18.5. Nothing used is newer than Node 22. |
| D-004 | setup | `scripts/banned-words.txt` holds the team's list (eight words and phrases; the file is the only place they're written). Matching is whole-word and case-insensitive. The check skips node_modules, build output, test files, the list and its checker, and the two vendored specifications (`docs/BACKEND_SPEC.md`, `docs/FRONTEND_SPEC.md`), which quote the words only to forbid them. A second rule keeps "test", "mock", "sample", "safe" and the rest of the frontend spec's list off **family screens** (en/hi strings outside the Lab, Guard, Diagnostics and simulation namespaces). The two sentences the frontend spec dictates word for word (`family.inperson`, `limits.closing`) are allowed. | Decided by the team (2026-09-26), plus frontend spec lines 785, 833, 1521 and 1708. |
| D-005 | setup | No domain yet: infrastructure files use `yourdomain.in` placeholders read from environment variables. Local development and every automated test use rpId `localhost` (a secure context). | Decided by the team (2026-09-26). Passkeys are bound to the rpId forever (5.3), so production waits for the real domain. |
| D-006 | setup | One git commit per phase, after that phase's gate is green. | Decided by the team (2026-09-26), matching Part A3. |
| D-007 | 0 | Frontend names follow the **code** (`apps/web`), behaviour follows the spec. The mapping is in `BUILD_PLAN.md` §2. | Spec B4. |
| D-008 | 0 | `SimKey` becomes a **software WebAuthn authenticator**: a P-256 key in IndexedDB that produces genuine ES256 answers (authenticatorData with the rpId hash and UP/UV flags, clientDataJSON with the challenge, a DER signature), after the simulated unlock sheet. `SimVerifier` runs the same `packages/crypto` verifier as `RealVerifier`; the only difference is where the expected origin and rpId come from (`location` instead of the build configuration). | APP-01 requires every combination of `SIM_RELAY`, `SIM_KEY` and `SIM_VERIFIER` to work. A second, weaker verification path would be a place for a false green to hide. |
| D-009 | 0 | Request IDs are ULIDs (26 characters), and a request's `send` frame uses the request ID as its message `id`, as in Appendix A. | 16.2 requires ULID message IDs; Appendix A shows the two equal. |
| D-010 | 0 | `lab.release { heldId, replacement? }`: `replacement` is the new `plain` payload only. The relay keeps the held frame's `kind`, `from`, `to` and `re`. | The spec doesn't define `replacement`. Replacing only the payload means the Lab can never re-address a frame. |
| D-011 | 0 | The relay sends Web Push with `web-push`'s `generateRequestDetails` and its own HTTP client. When `ENV_NAME=test` (and only then; config validation refuses it elsewhere), `PUSH_TEST_TARGET` sends every push request to a local mock push service, keeping the real endpoint host in the URL for the SSRF allowlist. | PSH-01 … PSH-08 need a mock push service that decrypts payloads (RFC 8291). The allowlist stays exactly as 11.3 says. |
| D-012 | 0 | Lab password hashes are Argon2id, verified with `hash-wasm` (WebAssembly, no native build). | 14.1 requires Argon2id. A pure implementation builds identically for `linux/arm64` and `linux/amd64` (18.5). |
| D-013 | 0 | New-phone guard matching (6.5): a card has "the same name" as a member when its normalised name (case-folded, spaces collapsed) equals that member's name or label, or its first word equals their first name or label. "The same phone number" means the last 10 digits match. | The spec doesn't define "same". Wider matching fails closed: a false warning costs one in-person re-add, a miss could add an impostor. |
| D-014 | 0 | The asker's phone number (the frontend's `fromPhone` extension) is **not** carried on the wire. The answerer shows a call-back number only from its own family list. | 7.4 defines the `verify.request` payload exactly, and inbound schemas are `.strict()`. |
| D-015 | 0 | The PIN fallback (10.10, tier P2) is not built. A6 follows FC-24 on every build: without passkeys the person continues as checks-only. The frontend's simulation-only PIN extension is removed. | No phase in Part D builds 10.10, and its wire shape isn't specified (see OPEN_QUESTIONS Q-5). |
| D-016 | 0 | The relay is a factory, `createRelay(config)`, with no module-level state. Integration tests run two gateways in one process on different ports, and one suite drives real child processes for signals. | 21.2 needs two gateways. Keeping no module-level state also means nothing leaks between gateways. |
| D-017 | 0 | In real mode, `RelayService.onPresence` reports the devices whose last `presence.query` answer was `online` or `push` (12). | 12 has no subscriptions; the app asks when a screen needs it. |
| D-018 | 0 | Each integration test file gets its own Valkey `KEY_PREFIX` (keys and pub/sub channels) and its own Postgres schema, with the migrations applied into it. | Phase 1 build list; lets suites run in parallel. |
| D-019 | 0 | The ULID generator lives in `packages/protocol` as plain code using `globalThis.crypto.getRandomValues`. | Both the app and the relay need it. It adds no dependency, so the package stays "zod only". |
| D-020 | 0 | `lab.held.frame` is the complete `deliver` frame the relay would have sent. The Lab page edits `frame.body.plain` and returns it as `replacement` (D-010). | Lets the Lab show exactly what was intercepted. |
| D-022 | 1 | The relay uses `ioredis` 5.11 (the mature line), not 6.0. | 6.0 (July 2026) switched the default wire protocol to RESP3; the relay's Lua replies and pub/sub are written against RESP2 semantics. |
| D-023 | 2 | Card v2 accepts `kt: "pk"` only. A card declaring `kt: "pin"` is refused as corrupt. | The PIN fallback isn't built (D-015); a card whose answers can't be verified must not look verifiable. |
| D-024 | 2 | An answer whose opened payload fails its schema is treated like an unreadable seal: INVALID `changed`, other checks skipped (9.4). | 9.3 says never trust the shape; "can't be read" is the same situation as a failed seal, and INVALID tells the truth. |
| D-025 | 2 | Relay → app frames are parsed leniently (unknown fields dropped) and never throw; app → relay frames and all payloads are strict. The relay validates `plain` payloads against their kind's schema too. | 7.2, 7.6, 9.3. |
| D-026 | 2 | The Lab's "held message timed out" report is a `lab.state` frame with `notice: "held_timeout"`. | 14.3 says the relay "reports 'Lab didn't respond'" without naming a message. |
| D-027 | 2 | Base64url decoding is strict (no padding, no stray trailing bits), so every byte string has one text form. | Removes a class of "same bytes, different string" comparisons (for example credential IDs in check 2). |
| D-021 | 0 | The Security Lab page labels devices from what it sees in plain traffic (`fromName`, `claimedLabel`), falling back to a short device ID. The relay never learns names. | 0 rule 5: the server stores no names. |

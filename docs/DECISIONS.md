# Decisions

Where the specification is silent, the code chooses the safer behaviour and records it here (CLAUDE.md, spec B4).
Each entry names the phase that made it. Security-, wire- or screen-changing questions go to `OPEN_QUESTIONS.md` first.

| ID | Phase | Decision | Why |
|---|---|---|---|
| D-001 | setup | The monorepo root is `Pehchaan/`. The finished frontend was **copied** into `apps/web`; the old `Pehchaan/frontend/` folder (a stale copy) and the two original specification files at the root (byte-identical to `docs/BACKEND_SPEC.md` and `docs/FRONTEND_SPEC.md`) were deleted in Phase 5, as the team asked. | Decided by the team (2026-09-26). The build session was running inside `frontend/`, and Windows cannot move a folder a process is using. |
| D-002 | 1 | Type checking uses **TypeScript 7** (`tsc`, the native compiler) in every package. ESLint uses `typescript-eslint` 8 with **TypeScript 6.0** installed only at the repository root, as the parser's library. Lint rules are the non-type-aware recommended sets. | TypeScript 7 ships no JavaScript compiler API, and `typescript-eslint` supports TypeScript `<6.1`. pnpm's isolation gives each package its own `tsc`. |
| D-003 | 1 | Code targets **Node 22** APIs, Docker images use `node:22-bookworm-slim`, and `engines` is `>=22`. The build machine runs Node 24 LTS, which is compatible. | Spec section 3 and 18.5. Nothing used is newer than Node 22. |
| D-004 | setup | `scripts/banned-words.txt` holds the team's list (eight words and phrases; the file is the only place they're written). Matching is whole-word and case-insensitive. The check skips node_modules, build output, test files, the list and its checker, and the two vendored specifications (`docs/BACKEND_SPEC.md`, `docs/FRONTEND_SPEC.md`), which quote the words only to forbid them. A second rule keeps "test", "mock", "sample", "safe" and the rest of the frontend spec's list off **family screens** (en/hi strings outside the Lab, Guard, Diagnostics and simulation namespaces). The two sentences the frontend spec dictates word for word (`family.inperson`, `limits.closing`) are allowed. | Decided by the team (2026-09-26), plus frontend spec lines 785, 833, 1521 and 1708. |
| D-005 | setup | No domain yet: infrastructure files use `yourdomain.in` placeholders read from environment variables. Local development and every automated test use rpId `localhost` (a secure context). | Decided by the team (2026-09-26). Passkeys are bound to the rpId forever (5.3), so production waits for the real domain. |
| D-006 | setup | One git commit per phase, after that phase's gate is green. | Decided by the team (2026-09-26), matching Part A3. |
| D-007 | 0 | Frontend names follow the **code** (`apps/web`), behaviour follows the spec. The mapping is in `BUILD_PLAN.md` §2. | Spec B4. |
| D-008 | 0 | `SimKey` becomes a **software WebAuthn authenticator**: a P-256 key in IndexedDB that produces genuine ES256 answers (authenticatorData with the rpId hash and UP/UV flags, clientDataJSON with the challenge, a DER signature), after the simulated unlock sheet. `SimVerifier` runs the same `packages/crypto` verifier as `RealVerifier`; the only difference is where the expected origin and rpId come from (`location` instead of the build configuration). | APP-01 requires every combination of `SIM_RELAY`, `SIM_KEY` and `SIM_VERIFIER` to work. A second, weaker verification path would be a place for a false green to hide. |
| D-009 | 0 | Request IDs are ULIDs (26 characters), and a request's `send` frame uses the request ID as its message `id`, as in Appendix A. | 16.2 requires ULID message IDs; Appendix A shows the two equal. |
| D-010 | 0 | `lab.release { heldId, replacement? }`: `replacement` is the new `plain` payload only. The relay keeps the held frame's `kind`, `from`, `to` and `re`. | The spec doesn't define `replacement`. Replacing only the payload means the Lab can never re-address a frame. |
| D-011 | 0 | The relay sends Web Push with `web-push`'s `generateRequestDetails` and its own HTTP client. When `ENV_NAME=test` (and only then; config validation refuses it elsewhere), `PUSH_TEST_TARGET` sends every push request to a local mock push service, keeping the real endpoint host in the URL for the SSRF allowlist. | PSH-01 … PSH-08 need a mock push service that decrypts payloads (RFC 8291). The allowlist stays exactly as 11.3 says. |
| D-012 | 0 | Lab password hashes are Argon2id, verified with `hash-wasm` (WebAssembly, no native build). | 14.1 requires Argon2id. A pure implementation builds identically for `linux/arm64` and `linux/amd64` (18.5). |
| D-013 | 0 | New-phone guard matching (6.5): a card has "the same name" as a member when its normalised name (case-folded, spaces collapsed) equals that member's name or label, or its first word equals their first name or label. "The same phone number" means the last 10 digits match. | The spec doesn't define "same". Wider matching fails closed: a false warning costs one in-person re-add, a miss could add an impostor. |
| D-014 | 0 | The asker's phone number (the frontend's `fromPhone` extension) is **not** carried on the wire. The answerer shows a call-back number only from its own family list. | 7.4 defines the `verify.request` payload exactly, and inbound schemas are `.strict()`. |
| D-015 | 0 | The PIN fallback (10.10, tier P2) is not built. A6 follows FC-24 on every build: without passkeys the person continues as checks-only. The frontend's simulation-only PIN extension is removed. | No phase in Part D builds 10.10, and its wire shape isn't specified (see OPEN_QUESTIONS Q-5). |
| D-016 | 0 | The relay is a factory, `createRelay(config)`, with no module-level state. Integration tests run two gateways in one process on different ports, and one suite drives real child processes for signals. | 21.2 needs two gateways. Keeping no module-level state also means nothing leaks between gateways. |
| D-017 | 0 | In real mode, `RelayService.onPresence` reports the devices whose last `presence.query` answer was `online` or `push` (12). | 12 has no subscriptions; the app asks when a screen needs it. |
| D-018 | 0 | Each integration test file gets its own Valkey `KEY_PREFIX` (keys and pub/sub channels) and its own Postgres schema, with the migrations applied into it. | Phase 1 build list; lets suites run in parallel. |
| D-019 | 0 | The ULID generator lives in `packages/protocol` as plain code using `globalThis.crypto.getRandomValues`. | Both the app and the relay need it. It adds no dependency, so the package stays "zod only". |
| D-020 | 0 | `lab.held.frame` is the complete `deliver` frame the relay would have sent. The Lab page edits `frame.body.plain` and returns it as `replacement` (D-010). | Lets the Lab show exactly what was intercepted. |
| D-022 | 1 | The relay uses `ioredis` 5.11 (the mature line), not 6.0. | 6.0 (July 2026) switched the default wire protocol to RESP3; the relay's Lua replies and pub/sub are written against RESP2 semantics. |
| D-023 | 2 | Card v2 accepts `kt: "pk"` only. A card declaring `kt: "pin"` is refused as corrupt. | The PIN fallback isn't built (D-015); a card whose answers can't be verified must not look verifiable. |
| D-024 | 2 | An answer whose opened payload fails its schema is treated like an unreadable seal: INVALID `changed`, other checks skipped (9.4). | 9.3 says never trust the shape; "can't be read" is the same situation as a failed seal, and INVALID tells the truth. |
| D-025 | 2 | Relay → app frames are parsed leniently (unknown fields dropped) and never throw; app → relay frames and all payloads are strict. The relay validates `plain` payloads against their kind's schema too. | 7.2, 7.6, 9.3. |
| D-026 | 2 | The Lab's "held message timed out" report is a `lab.state` frame with `notice: "held_timeout"`. | 14.3 says the relay "reports 'Lab didn't respond'" without naming a message. |
| D-027 | 2 | Base64url decoding is strict (no padding, no stray trailing bits), so every byte string has one text form. | Removes a class of "same bytes, different string" comparisons (for example credential IDs in check 2). |
| D-028 | 3 | A grant is `"<grantId>.<secret>"` (8 and 16 random bytes, base64url). Its registered hash is SHA-256 of the secret's **bytes**, sent as base64url in `grant.set.hash`. | 6.4 says "SHA-256(secret)" without fixing the encoding; hashing the bytes makes the text form irrelevant. |
| D-029 | 3 | `contact.revoke` for a device the relay has never seen is a no-op: such a device can hold no binding, and Remove also resets my code by default. | A binding row needs both device rows (the schema's foreign keys). The grant rotation closes the gap. |
| D-030 | 3 | Control messages (`grant.set`, `contact.*`, `push.*`, `cancel`, `device.retire`) are confirmed with `receipt { of, state: "accepted" }`. A refused `send` gets both `error { code, of }` and `receipt { state: "rejected", reason }`; `rate_limited` and `unavailable` get only the error, and the app may re-send the same id. | 8.4 defines receipts for sends and 7.5 errors for refusals; confirming control messages lets the app's outbox settle them the same way. |
| D-031 | 3 | The per-socket frame limit (20/s, burst 40) runs the same GCRA in memory; every other 16.1 row runs the Lua script in Valkey. | A socket lives on one process; a Valkey round trip per frame would add load for nothing. |
| D-032 | 3 | Connection limits that are close codes (4429 for the per-IP connection rate and the 20 pending sockets per IP) are applied just after the upgrade, so the app can read the code. Origin (403), subprotocol (426) and capacity (503) are refused before it, as HTTP. | 7.1, 7.5: 4429 is a close code; 403/426/503 are HTTP statuses. |
| D-033 | 3 | In `development` and `test`, the relay applies migrations at start. In staging and production they run as a separate deploy step before the new version starts (`dist/migrate.js`). | 15.2 and 18.8 require migrations before the new version; on a laptop the extra step only gets in the way. |
| D-034 | 3 | Import cycles through `import type` edges are allowed; runtime import cycles are not (depcruise `no-circular` ignores type-only edges). | Type-only imports vanish at runtime; the relay's `Hub` type naturally refers to the connection type and back. |
| D-021 | 0 | The Security Lab page labels devices from what it sees in plain traffic (`fromName`, `claimedLabel`), falling back to a short device ID. The relay never learns names. | 0 rule 5: the server stores no names. |
| D-035 | 5 | The app's IndexedDB goes to version 2 (identity, simulated key, outbox, push inbox; used nonces keep their request ID). The upgrade **clears** version-1 data (profile, family, history, alerts, requests). | v1 cards have no device keys or grant and can't reach the real relay; keeping them would show a family that can't be checked. The frontend has never shipped to users. |
| D-036 | 5 | Every time shown on a phone is that phone's own: E1/E2 "{label}'s key · N s ago" uses when *this* phone received the answer, and a received family alert is timed by when it arrived. The other phone's `answeredAt` / `createdAt` are carried but never compared with this clock. | 8.7 and CLAUDE.md ("never compare another device's timestamps with this device's clock"). Found by the F-15 clock-skew journey. |
| D-037 | 5 | The asking, verdict and answering screens (`verify`, `Result`, `answer` chunks) load as soon as the app starts, not at idle. A code chunk that fails to load while the phone is **offline** no longer reloads the page (which would show the browser's "no internet" page); the error screen waits and reloads when the network is back. | A check must end on a Pehchaan verdict screen even if the network drops mid-check (fail closed, never blank). Found by J-05. |
| D-038 | 5 | "Reset my code" and Remove's revoke/unrevoke must reach the relay even if the phone is offline at that moment: the rotation is marked pending (finished by the next login with `rotate: true`), and revoke/unrevoke wait in a small persistent queue sent in order on every connection (the latest operation per device wins). | 6.4. A reset that silently didn't happen would leave an old card working. |
| D-039 | 5 | The D1 "may not get this" hint appears for a member the relay reports `offline`. Because presence only answers for devices the asker may contact (12), a member never checked yet also shows the hint until the first check creates the binding. | 12 defines both rules; the hint says "may not", and the check can still be sent. |
| D-040 | 5 | Local development (`pnpm dev`): the relay reads `apps/relay/.env.development` (committed: it holds no secrets) and Vite proxies `/relay` to it, so the app and the relay share one origin; `RELAY_HOST` is the Vite server's host. The real-backend Playwright suite starts its own relay (Postgres schema `e2e`, key prefix `e2e:`) and app on ports 8081/5181; the simulated walkthrough uses its own port (5190) and never reuses a running server. | 18.12. Reusing whatever is on a port once ran a suite against the wrong app. |
| D-041 | 5 | A deleted passkey can't be told apart from a cancelled prompt (WebAuthn reports both as `NotAllowedError`). F1 shows F5 after each failed unlock, and from the second one on the same request adds "Your key may be missing from this phone. Set it up again…" with a button to My key. | Spec 23 asks for "F5, then 'Your key is missing'" without a way to know; saying "may be" stays true when the person simply cancelled twice. |
| D-042 | 6 | During a VAPID rotation (11.9) the relay holds the current key and, optionally, the previous one (`VAPID_PREVIOUS_KEY_ID/PUBLIC_KEY/PRIVATE_KEY`, all three or none, the ID different from `VAPID_KEY_ID`). Each subscription is pushed with the key it names; a subscription naming a key the relay no longer has is marked expired, and the app re-subscribes at its next login. | 11.9 step 2 ("deploy the relay with both keys") needs somewhere to put the second key. Expiring rather than guessing a key fails closed. |
| D-043 | 6 | `POST /v1/push/resubscribe` is signed over `"pehchaan-resubscribe-v1\n" + RELAY_HOST + "\n" + deviceId + "\n" + endpoint + "\n" + ts`, with the same ±120 s window and rate limit as `/v1/inbox/fetch`. | 11.2 says "signed with the device key the same way as the inbox fetch in 11.4" without giving the string. A different first line keeps a fetch signature from being replayed as a re-subscription; the endpoint is signed so it can't be swapped. **Needs the team's confirmation (wire format).** |
| D-044 | 6 | The service worker never accepts a readable (plain) envelope, even from a phone opted in to the Security Lab: such a push shows the generic "Open Pehchaan." notification, and the open app handles the frame. | The service worker can't know whether the open app has opted in (14.2); the safer side is to show nothing it couldn't check. |
| D-045 | 6 | A rate limit whose `retryAfterMs` outlasts the message (e.g. the fourth alert check in an hour, 11.8) is refused at once with the relay's reason, instead of being held until the message expires and reported as "unreachable". Shorter limits are still waited out and re-sent (8.4). | The person learns "3 alert checks an hour" instead of a misleading network error. |
| D-046 | 6 | A8 appears after A7 for everyone, whenever this phone can receive pushes (a real relay, a VAPID key, the Push API) and alerts are off; for "checks only" it adds that alerts also bring family alerts. It never appears with the simulated relay. On an iPhone in a Safari tab it explains that alerts need the Home Screen app. The `next` parameter only accepts this app's own paths. | 11.2 ("part of normal setup for the can-be-verified role, strongly recommended for everyone else"); section 22 retires ENABLE_EXTRAS for A8. |
| D-047 | 6 | The alert check's arrival time is the service worker's receive time minus the tap time, both on this phone's clock. Every notification is closed by the app once its screen shows (F1 for `req-<id>`, the verdict for `ans-<id>`). | 8.7 (never compare with the relay's clock); 11.5. |
| D-048 | 6 | In the real-backend journeys, the phone's browser is given a push subscription created by the test (real P-256 keys, an allowlisted endpoint), because a test browser can't reach Google's push service. Everything else is real: A8, `push.subscribe`, the relay's RFC 8291 encryption and VAPID signature, which the stand-in push service verifies and decrypts. Each run uses a throwaway VAPID pair generated at start. A closed app's passkeys are carried to the reopened page, as a phone keeps them. | J-06 without an external service; real phones are covered by E4 steps 9–12. |
| D-049 | 7 | The Lab module's code is imported only when `LAB_ENABLED=true` (a dynamic import in `createRelay`). Lab page sessions, opt-ins and armed attacks live in Valkey with their TTLs (4 h, 4 h, 15 min); a held message is taken with `GETDEL`, so a release, an injection or the 10 s timeout acts exactly once whichever gateway gets it. | 14.1 layer 1; two gateways must never both forward a held message. |
| D-050 | 7 | The relay sends the Lab page each message's readable `plain` payload and a bare kind; the page writes the summary line itself (`services/labSummary.ts`, shared with SimLab). A sealed message is shown as "sealed" and, if held, released unchanged. | Keeps the relay from interpreting payloads (it only forwards what both opted-in phones chose to send readable). |
| D-051 | 7 | `lab.inject` accepts only `verify.answer`, and runs the same request-record script as a genuine answer (`mayInject` → `requests.answer`): the injected answer must name a target of an open request and go to its asker, once. A report on a request the Lab didn't tamper with (or whose hold timed out) writes no `lab_attacks` row. A `VERIFIED` report on a tampered request is recorded as a false green, counted in the metric and logged at error level. | 16.3 row 11; 14.3 honesty rule; 14.4. |
| D-052 | 7 | The Lab password needs at least 12 characters (`infra/scripts/lab-password-hash.ts`), hashed with Argon2id (m = 64 MiB, t = 3, p = 1). Wrong and right attempts both count against the per-IP limit shared by `lab.join` and `lab.optin`. A Lab page remembers its 4-hour session locally and asks for the password again when the relay answers `lab_denied`. | 14.1 layer 2; the spec gives no length, so the safer choice. |
| D-053 | 7 | Call Guard's paired phones are stored on the laptop (`guard:targets`) with only what a sealed prompt needs (device ID, grant, device and encryption keys) plus the name and safety words. Pairing needs the four words to be confirmed as matching. | 13.2. |
| D-054 | 7 | The real-backend Playwright relay runs with `LAB_ENABLED=true` (the switch stays off until a test runs `admin lab on`), a Lab password hash made at start by the team's own script, and `RATE_LIMIT_PROFILE=relaxed`: J-12's 50 checks between two phones would otherwise hit the 3-a-minute pair limit. Every limit is still enforced (at 100×); the standard limits are covered by the relay integration tests. | J-12 in minutes; relaxed is refused in production (config). |
| D-055 | 7 | The Lab page shows an attack as "Armed" only after the relay has accepted `lab.arm`, never on the tap. A check sent before that is not intercepted, and saying "Armed" then would be untrue. | 14.3; found by J-12 under load. |
| D-056 | 7 | The Lab page acts on a held message at once, with no timer: a page in a background tab has its timers throttled (to once a minute after a while), and the relay releases a held message unchanged after 10 s. The traffic log and pipeline still show each step. | Found by J-12: attacks stopped firing after a few minutes in a background window. A missed attack only lets the genuine message through; it can never cause a false green. |
| D-057 | 9 | gitleaks keeps every default rule and exempts exactly one file, `apps/web/src/store/seedKeys.ts`: the fixed keys of the simulated devices, loaded only by simulation tabs, which protect nothing (`.gitleaks.toml`). | SEC-10 found them; they are test fixtures, not secrets. | D-059 | 8 | The relay can write every WebSocket frame to a file (`FRAME_CAPTURE_FILE`), refused by the configuration outside `ENV_NAME=test`.
